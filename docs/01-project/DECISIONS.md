# ADR-025

Title: Build Tooling And Library Versions

Status: Accepted

Date: 2026-10-13

## Context

TECH_STACK.md selects Vite as build tool, React, Electron and Zod.

No build or configuration file exists yet (Phase 1 - Project Bootstrap). TypeScript checks are run outside the repository.

The Electron main process and preload bridge are located in src/electron/ (main.ts, preload.ts). The renderer is located in src/gui/.

The React version is "Latest Stable" in TECH_STACK.md, which does not identify a reproducible version.

The validation code uses the Zod 3 API (.passthrough(), z.ZodIssueCode) in src/schemas/.

The Electron version is not defined in TECH_STACK.md.

Electron supports the three latest stable major versions. On 2026-10-13, the supported versions are (planned end of support from the Electron release schedule):

- Electron 42: 2026-10-20
- Electron 43: 2027-01-05
- Electron 44: 2027-03-02 (latest stable, 44.7.0)

Electron 45 is in beta; its stable release is planned for 2026-10-20.

## Decision

Build Tool:

- Vite builds the renderer.
- vite-plugin-electron builds the Electron main process (src/electron/main.ts) and the preload bridge (src/electron/preload.ts) with the same Vite configuration.
- Renderer entry: index.html at the repository root, and src/gui/main.tsx.

Library Versions:

- React: major version 18.
- Zod: 3.25.x, installed from Phase 1.
- Electron: major version 44 (44.7.0 or a later 44.x patch release; 44.9.3 since CHANGELOG 0.1.65, fix of GHSA-jr5w-w6x2-84p9).
- Tailwind CSS: major version 4, through the @tailwindcss/vite plugin; the styles entry point is src/gui/styles/global.css (no Tailwind configuration file).
- Content Security Policy: vite.config.mts adds a meta tag to index.html, strict for the built application and adapted for the development server (SECURITY_SPEC.md, Renderer Content Security Policy).
- Bundle size warning: build.chunkSizeWarningLimit is 1500 kB in vite.config.mts. The renderer bundle includes Three.js (about 950 kB in Phase 4); it is loaded from disk by Electron, so its size does not slow the start of the application. The bundle is not split; the raised limit still reports an unexpected growth.
- Lucide React: major version 1 (lucide-react).
- shadcn/ui: installed with the shadcn command line tool (shadcn init); components are copied into the repository and use the "@/" import alias, which designates src/ (tsconfig.json paths and Vite resolve.alias).
- shadcn/ui settings (components.json): component library Base UI (@base-ui/react), style base-nova (preset Nova), Lucide icons; components in src/gui/components/ui/, utils alias src/utils/cn.ts.
- Right-to-left (components.json "rtl": true, set by shadcn migrate rtl): shadcn/ui components use logical classes (ms, me, ps, pe, start, end) instead of left and right, so that they follow the text direction of Hebrew; components added later are generated in this form.
- Font: Inter (@fontsource-variable/inter), fallback Segoe UI, Roboto, sans-serif (GUI_SPEC.md, Font), instead of the Geist font of the Nova preset.
- Hebrew font: Inter has no Hebrew glyphs. Noto Sans Hebrew (@fontsource-variable/noto-sans-hebrew, major version 5) is placed right after Inter in the font stack: Hebrew characters use it, Latin text stays in Inter; its Hebrew file is only loaded when Hebrew text is displayed (unicode-range).
- Resizable panels: shadcn/ui Resizable component (shadcn add resizable), on react-resizable-panels major version 4 (Group, Panel, Separator; numeric sizes are pixels, strings without unit are percentages).

Electron 44 is the latest stable major version and the supported version with the longest remaining support. It embeds Node.js 24 and Chromium 152.

Before the end of support of Electron 44 (planned 2027-03-02), the project moves to a supported major version.

A change of the major version of one of these tools is recorded in this document before implementation.

# ADR-026

Title: Object-Scoped Analysis And Recommendations

Status: Accepted

Date: 2026-10-09

## Context

A project may contain several objects (PROJECT_SPEC.md section 4.5).

Target slicer export requires a Recommendation for every exported object (SLICER_EXPORT_SPEC.md, error EXP_003).

DATA_SCHEMA.md 2.0.0 stores a single analysis and a single recommendations block per project.

Neither the Complete Analysis Schema nor the Recommendation Schema identifies the object it belongs to.

Recommendation.analysisId has no target, because no analysis schema defines analysisId.

## Decision

Analysis and recommendations are scoped to one object.

- Complete Analysis Schema gains analysisId, objectId and status.
- Recommendation Schema gains objectId. Its existing status field gets defined values.
- Status values: generated, outdated.
- In the Project Schema, analysis and recommendations remain objects, indexed by objectId.
- Object Reference Rules define integrity, removal, duplication and transformation behavior.

Object lifecycle:

- Removal: the analysis and the recommendation of the object are removed.
- Duplication: the copy receives a new objectId and inherits no analysis and no recommendation.
- Rotation or scaling: the analysis and the recommendation become outdated and must be recomputed before any export.

Schema changes in DATA_SCHEMA.md are additive. No field is removed, renamed or retyped.

API_SPEC.md contains one non-additive change: the response of Generate Recommendation replaces the field recommendation with recommendations, indexed by objectId. The API is not implemented yet; no consumer requires migration.

DATA_SCHEMA.md becomes 2.1.0. The WYPROJ format version remains 2.0.0.

## Consequences

Advantages:

- One analysis and one recommendation per object, enforced by the structure
- Target slicer export validation (EXP_003) becomes verifiable
- Results computed for a previous orientation or scale are never exported
- Recommendation.analysisId becomes resolvable
- Backward compatible with DATA_SCHEMA.md 2.0.0

Disadvantages:

- The recommendation response of API_SPEC.md changes from a single recommendation to one recommendation per object
- Types, Zod schemas and stores must move from a single result to results per object
- Scene and transform operations must update analysis and recommendation status

## Alternatives Considered

Arrays of analyses and recommendations in the Project Schema

Rejected

Reason:

- Changes the type of existing fields
- Does not enforce one recommendation per object

Single project-level recommendation applied to every object

Rejected

Reason:

- Contradicts SLICER_EXPORT_SPEC.md
- Objects of different categories require different settings

# ADR-028

Title: Viewport Coordinate System And Viewport Domain Direction

Status: Accepted

Date: 2026-10-16

## Context

Phase 4 (3D Viewport) creates the build plate, the grid, the axes and the camera.

Three.js uses the Y axis up by default. 3D printers, slicers and STL and 3MF files use the Z axis up.

DATA_SCHEMA.md (Transform Schema) stores object positions, without stating their origin.

PRINTER_PROFILE_SPEC.md (Build Plate Origin) allows printers with the origin at the center, at the front left corner, or custom.

No printer can be selected before Phase 7 (Printer Database).

DOMAINS_DEPENDENCY_MATRIX.md allowed the Viewport Domain to depend on the GUI Domain, but not the GUI Domain to depend on the Viewport Domain, while the main window (GUI) must display the viewport.

## Decision

Coordinate system of the viewport and of the project:

- Units: millimeters.
- Axes: X to the right, Y to the back, Z up.
- Origin: center of the build plate, Z = 0 on the plate surface.
- transform.position (DATA_SCHEMA.md) is expressed in this coordinate system, whatever the printer. The origin of the printer is applied only when exporting to the target slicer.

Build plate:

# ADR-030

Title: 3MF Import With fflate And fast-xml-parser In The Web Worker

Status: Accepted

Date: 2026-10-16

## Context

TECH_STACK.md (3MF Support) named the 3MFLoader of the three.js examples.

3MFLoader reads the XML parts with DOMParser, which does not exist in a Web Worker (ADR-029), and it does not convert the units of the file.

3MF files exported by Bambu Studio and OrcaSlicer store each object in its own model part (3D/Objects/*.model) and reference it with the Production extension (attribute p:path of a component). They often contain several objects already placed on the build plate.

## Decision

- The 3MF file is parsed in the Web Worker with two libraries: fflate (ZIP archive) and fast-xml-parser (XML). 3MFLoader is not used.
- fast-xml-parser checks that each XML part is well-formed (XMLValidator), then reads it tag by tag (updateTag); the tags are not kept, so no XML tree is built in memory.
- Supported: units (micron, millimeter, centimeter, inch, foot, meter, converted to millimeters), build item transforms, components with their transforms, model parts referenced with the Production extension.
- Each build item becomes one object; the meshes of its components are merged into it. Objects of type "other" are not printed (3MF Core Specification): they are not imported (for example the modifier parts of Bambu Studio).
- Placement: the objects of one 3MF file keep their layout; the group is centered on the origin and its lowest point is at Z = 0 (ADR-028, ADR-029).
- Security: archive extraction limits (SECURITY_SPEC.md, Archive Extraction Limits); DOCTYPE refused, entities not processed.
- Amendment (2026-10-17, CHANGELOG 0.1.45): the ZIP archive is read from its central directory by a reader of the project (src/importer/ZipReader.ts), and each part is decompressed by chunks with the Inflate stream of fflate, stopped as soon as it produces more than its declared size. fflate unzipSync stops writing at the declared size but still inflates all the data (a header that lies about the size keeps the worker busy for minutes); the streaming Unzip of fflate cuts a part with a data descriptor (flag bit 3, used by Bambu Studio) where the bytes of the data descriptor signature appear by chance, and its terminate() does nothing in synchronous mode.
- An import can be cancelled by the user: the reading is aborted or the worker is terminated.

## Consequences

Advantages:

- Window responsive with large 3MF files, with progress
- Units and layout of the file respected
- Bambu Studio and OrcaSlicer files supported

Disadvantages:

- Two new dependencies (fflate, fast-xml-parser)
- Parsing a very large 3MF file is slower than an STL file of the same size (generic XML parser and validation)
- Several build plates of Bambu Studio are imported as one layout (KNOWN ISSUES: KI-019)

## Alternatives Considered

3MFLoader on the main thread of the renderer

Rejected

Reason:

- The window would freeze without progress while a large file is parsed; units not converted

3MF XML reader written for the project

Rejected

Reason:

- A proven XML parser is preferred

# ADR-031

Title: Object Transform Meaning (Rotation Unit, Order, Pivot, Scale)

Status: Accepted

Date: 2026-10-18

## Context

Phase 6 (Transform System) moves, rotates and scales objects. The Transform Schema (DATA_SCHEMA.md) gave rotation x, y, z without unit, order or pivot, and did not say how scale and rotation combine (KI-017). The values are saved in WYPROJ files and converted at export (3MF build item transform).

## Decision

- Rotation unit: degrees.
- Sign: right-hand rule (a positive angle turns counterclockwise seen from the positive end of the axis).
- Order: around the axes of the build plate, first X, then Y, then Z: R = Rz · Ry · Rx (Euler order "ZYX" of Three.js).
- Scale: along the axes of the object, applied before the rotation.
- Pivot and position: the local origin of the object is the center of the base defined at import (center in X and Y, lowest point in Z); position is the place of this point on the plate. After a rotation, this point is not necessarily at the bottom of the object.
- Point on the plate = position + R · (S · point of the object).
- After each change of rotation or scale, the object is placed back on the plate (lowest point at Z = 0), as in Bambu Studio, OrcaSlicer and PrusaSlicer.
- Export: 3MF build item transform = (R · S) transposed, translation = position + offset of the printer origin; mesh in the coordinate system of the object (DATA_SCHEMA.md, Transform Rules).
- The computation is in src/scene/ObjectTransform.ts (Scene Domain), used by the viewport and by the transform tools; it is checked by unit tests (Vitest, TECH_STACK.md).
- Amendment (2026-10-19, CHANGELOG 0.1.51, DATA_SCHEMA.md 3.4.0, decision of Noam): the local origin of an object is the center of its bounding box at import (X, Y and Z), no longer the center of its base. The object turns around its center, and its position is the place of its center: a rotation keeps position X and Y, as in Bambu Studio and OrcaSlicer; position Z is the height of the center. With the gizmo, the object turns freely during the gesture and is placed back on the plate on release (only Z changes). The export formula is unchanged (the mesh is exported relative to the local origin). No WYPROJ file was affected: projects are not saved yet (Phase 13).

## Consequences

Advantages:

- WYPROJ files readable (degrees)
- Same behavior as the target slicers
- Export transform defined before the export is written

Disadvantages:

- The renderer converts degrees to radians

## Alternatives Considered

Radians

Rejected

Reason:

- Less readable in project files; slicers show degrees

Rotation around the axes of the object (Euler order "XYZ")

Rejected

Reason:

- Rotating around Z after a tilt would not turn the object flat on the plate

Scale along the axes of the plate

Rejected

Reason:

- A rotation would change the shape of a stretched object (shear)

# ADR-032

# ADR-034

Title: Model Analysis Definitions and Methods

Status: Accepted

Date: 2026-11-01

## Context

Phase 9 (Model Analysis) computes the analysis of each object (Complete Analysis Schema, ADR-026). DATA_SCHEMA.md 3.8.0 gave the names of the fields, but not their meaning, their units or the content of dimensions and stability.centerOfGravity ({}). PHASES_IMPLEMENTATION_PLAN.md put Object Classification at the top of Phase 9, while its own table puts classification in Phase 10. The store of the analyses is ready (ADR-026), but nothing computes an analysis: the six files of src/model_analysis/ are templates of Phase 0 with wrong values (volume of the bounding box, angle always 45 degrees). No dependency of the project gives fast ray casting (BVH). Analysis: lot 75 (PHASE9-ANALYSE.md), decisions D1 to D10 of Noam (2026-11-01).

## Decision

- Scope (D1): Phase 9 computes the geometry only. Object Classification, Category Detection and Confidence Score move to Phase 10 (Classification and Recommendation Engine), with the recommendation. Until then, analysis.classification is null = "not yet classified" (DATA_SCHEMA.md 3.9.0), the same rule as the selections not yet made. A WYPROJ 3.0.0 file whose analysis has a classification stays valid: no change of the WYPROJ format. A recommendation is not generated while the classification is null (REC_002).
- Frame and units (D2): the analysis is made on the object as placed on the build plate: scale and rotation applied, position ignored (Object Reference Rules, rule 8). Units: mm, mm², mm³, degrees, percentage 0 to 100. dimensions {width, depth, height} = size on the plate along X, Y, Z; geometry = the same size, plus volume and surfaceArea after scale (Known Duplication); mesh = triangles and distinct vertices; stability.centerOfGravity {x, y, z} = center of gravity of a full and homogeneous solid, relative to the center of the object (transform.position), along the axes of the plate.
- Overhangs (D3): angle of a triangle facing down measured from the vertical (0 = vertical wall, 90 = flat ceiling), as the thresholds of SUPPORT_GENERATION_SPEC.md; triangles lying on the plate excluded; maxAngle = largest angle; percentage = area beyond 45 degrees (limit "Safe" of SUPPORT_GENERATION_SPEC.md) divided by the total area; detected = at least one triangle beyond 45 degrees.
- Bridges (D3): a flat region facing down (beyond 80 degrees), not on the plate, made of triangles joined by their edges; on its border, a triangle that goes down is a support (a wall that carries it), a triangle that goes up is a free edge. The region is a bridge when it has at least two separate supports; with one support it is an overhang only. count = number of bridges; longestBridge = the largest span, the span of a bridge being the shortest distance between two of its supports (the direction in which a slicer draws a bridge). This is an approximation: a curved or slanted bridge can be counted wrongly.
- Stability (D4, corrected by Noam): contactArea = real area of the triangles lying on the plate (at 0.01 mm), used for adhesion. The tip test and heightRatio use the convex hull, seen from above, of the contact points with the plate (the vertices at Z <= 0.01 mm), not only the area of the faces lying on the plate: an object on legs (chair, table, tripod, stool) is stable when its center of gravity is inside the hull of its legs. heightRatio = height divided by the square root of the area of the hull (0 when this area is 0); riskScore = (heightRatio - 1) x 20, rounded, limited to 0 and 100; 100 when the center of gravity, seen from above, is outside the hull, or when there is no contact area (a point or a line). Examples: cube of 20 mm: 0; tower of 20 x 20 x 100 mm: 80 (High); sphere: 100; stool on four legs: low. Levels of AI_ENGINE_SPEC.md (already in AnalysisConstants.ts). The coefficients are a first setting, which can be adjusted in Phase 10.
- Thin walls (D5): new dependency three-mesh-bvh (MIT, version 0.9.17, needs three >= 0.159), installed by Noam in lot 79, used in the Web Worker of the analysis. From points of the surface (at most 200 000, spread in proportion to the area, the same points at each computation), a ray goes towards the inside; the distance to the next face met is the thickness. A point is taken inside its triangle, never on an edge, and the ray ignores its own triangle, so that it never meets its own face or a neighbouring face at its start (test: a full cube of 20 mm gives 20 mm). minimumThickness = the smallest thickness, in mm; detected = below 0.8 mm (two lines of a 0.4 mm nozzle), whatever the printer: the comparison with the nozzle stays a recommendation (RECOMMENDATION_RULES.md, Phase 10).
- Meshes not closed (D6): the analysis is computed anyway. When an edge is not shared by exactly two triangles, a non-blocking message is shown (ANA_002, "Mesh not closed: volume and wall thickness are approximate"), like the messages of the import. No field is added to DATA_SCHEMA.md. Only an empty or unreadable mesh gives ANA_001 (no analysis).
- Start (D7): automatic, after the import of each object, and when an analysis becomes outdated (rotation or scale), once the gesture is over or the value confirmed (never while dragging). In a Web Worker (no Electron, KI-024), one object at a time; a computation that is no longer needed (object removed, or turned again) is dropped. Tools > Analyze Models (all objects without an analysis up to date) and Tools > Recompute Analysis (selected objects, computation forced) are enabled. The status bar shows "Analyzing…" during the computation.
- Analysis section (D8, option A): one selected object: status (Up to date, Outdated, Analyzing), dimensions L x W x H mm, volume in cm³ and area in cm² (the units of the slicers), mesh, overhangs, bridges, thin walls, stability with the level of the risk. Several objects: "Select a single object". Texts in the three languages. Option B (overhanging triangles in red in the 3D view) is accepted for a separate lot after the closure of Phase 9.
- Unused files (D9): GeometryAnalyzer.ts, StabilityAnalyzer.ts, PrintabilityAnalyzer.ts, MeshValidator.ts, MeshAnalyzer.ts and ModelAnalyzer.ts (src/model_analysis/) are rewritten with the real computations, under the same names (ModelAnalyzer builds the analysis; getPrintabilityScore disappears: no field in DATA_SCHEMA.md); AnalysisService.ts is rewritten (it starts the analysis, validates the result with AnalysisSchema and stores it; serialize, deserialize and isPrintable removed); src/gui/panels/AnalysisPanel.tsx is deleted when the Analysis section is done (lot 80). Each deletion is recalled in the LOTN.md of its lot.
- Size and time (D10): target added to PERFORMANCE_SPEC.md: 1 million triangles analyzed in less than 5 seconds on the computer of Noam, the interface staying fluid. Larger models are analyzed too (no new limit; the limits of the import stay), with "Analyzing…". The target is checked, it does not block.

## Consequences

Advantages:

- Each value of the analysis has a definition, a unit and a method that can be tested on models built in the tests
- The analysis does not depend on the printer or the material: changing them never makes it outdated
- Phase 9 stays limited to the geometry; classification gets its own rules in Phase 10

Disadvantages:

- One more dependency (three-mesh-bvh) to follow
- Bridges, and the volume and the thickness of a mesh that is not closed, are approximations
- The coefficients of the tip risk are a first setting

## Alternatives Considered

Analysis in the coordinate system of the imported file (without rotation or scale)

Rejected

Reason:

- The overhangs would not match the object as it will be printed (ADR-026)

Tip test on the faces lying on the plate only

Rejected (correction of Noam)

Reason:

- An object on legs would get a risk of 100 while it is stable

Threshold of the thin walls from the nozzle of the selected printer

Rejected

Reason:

- Changing the printer would make the analysis outdated (a new Object Reference Rule)

Search grid written for SlicyWeb instead of three-mesh-bvh

Rejected

Reason:

- More code to maintain and test for an equivalent result

# ADR-035

Title: Classification and Recommendation Rules

Status: Accepted

Date: 2026-11-05

## Context

Phase 10 (Classification and Recommendation Engine) classifies each object and recommends its print settings. The documents describe the categories with words ("Organic Shapes", "Open Top") and the settings with ranges or words ("Slow", "Reduce Speed"), rarely with a number. The code of src/classification_engine/ looks for keywords that nothing produces; no print preset exists (data/presets/ is empty); the recommendation ignores the printer, the material and the filament (KI-008); its confidence is the confidence of the preset only (KI-010); the recommended profile has no temperature (SLICER_EXPORT_SPEC.md, Required Data Model Extensions); the Support Schema of DATA_SCHEMA.md ({required, type, density, overhangThreshold}) differs from the code ({enabled, type}). Every number that the application proposes must therefore be written in the documentation and validated. Analysis: lot 83 (PHASE10-ANALYSE.md), decisions D1 to D13 of Noam (2026-11-05).

## Decision

- Scope (D1): Phase 10 contains the automatic classification with a choice of the user, the presets, the recommendation with the limits of the printer, the material and the filament, the warnings, the confidence, the automatic start and the interface. Out of Phase 10: orientation and optimization (Phase 11), cost (Phase 12), saving in a project (Phase 13), export, vase mode and values per target slicer (Phase 14, KI-012), manual choice of a preset, Custom preset, editing of the recommended values, preset library (Phase 15), HTTP API Generate Recommendation (KI-007 stays open).
- Automatic classification (D2): only what the geometry can show. Ten measured features with fixed lowercase names (small, large, tall, flat, planar, curved, holes, hollow, open_top, thin_walls), computed in the Web Worker of the analysis, with the thresholds of OBJECT_CLASSIFICATION_SPEC.md 1.2.0 (Geometric Features). Five category rules, the first that matches wins: vase (75), container (70), miniature (70), figurine (65), mechanical_part (65); otherwise unknown (0, Balanced preset, CLASSIFICATION_UNCERTAIN). The other nine categories are never chosen automatically. The automatic confidence never exceeds 75. The file name is not used. subcategory stays "" and detectedTags stays []. The thresholds are a first setting, checked on models built in the tests and on the models of Noam, and can be adjusted before the closure of Phase 10.
- Choice of the user (D3): in the Recommendation section, a list "Object type": "Automatic (category)" first, then the 15 categories. The choice belongs to each object and gives a confidence of 100. New field classification.source ("automatic" or "user", DATA_SCHEMA.md 3.10.0); a WYPROJ 3.0.0 file without it is read as "automatic"; no new version of the WYPROJ format. The choice is kept when the object is analyzed again (rotation, scale): the type of an object does not depend on its orientation. It is not part of Undo / Redo (transforms only, UNDO_REDO_SPEC.md). A duplicated object has neither analysis nor choice (Object Reference Rules, rule 7).
- Presets (D4): 11 presets shipped in data/presets/ (one JSON file each, Repository Data Schema envelope, type preset, source Official), read and validated by the main process (PresetSchema, strict), served by a new IPC channel preset:getAll (29 channels). Same path as the materials (ADR-033). No synchronization with slicyweb-profiles in Phase 10; no Custom preset and no preset of the user (Phase 15).
- Values of the presets (D5, corrected by Noam): the table of PRINT_PRESETS_SPEC.md 1.3.0 (Preset Values), speeds in mm/s. One single name for the tree supports in every preset: tree (Cura name; confirmed by Noam on 2026-11-05, answer A); the value organic is removed from the support types (the translation per target slicer stays in Phase 14, KI-012). No preset enables supports by itself: the type is used only when the geometry requires supports (D8). The fan is no longer a value of the preset: the field fanSpeed of the preset settings is removed (it comes from the filament or the material, D7). Wall and infill speeds stay 40, 80 and 120 mm/s, never above the print speed of the preset; travel 250 mm/s. The confidenceScore of the shipped presets is 100 and is no longer part of the confidence of the recommendation (D10). The vase mode itself (continuous spiral wall) has no field in the recommended profile: Known Issue for Phase 14.
- Limits (D6, corrected by Noam; KI-008): after the preset and the geometry: print speed at most maxPrintSpeed of the printer, or at most 100 mm/s when maxPrintSpeed is null (15 printers of 79, among them Ultimaker S5, S6, S7, Prusa MINI+, Raise3D Pro3, Flashforge Adventurer 5M); travel speed at most maxTravelSpeed, or at most 150 mm/s when it is null (prudent value proposed in lot 84, confirmed by Noam on 2026-11-05, answer C: without warning, the travel does not change the quality of the part); family TPU: print speed at most 30 mm/s; layer height at most 75 % of the default nozzle of the printer and between 0.08 and 0.28 mm; temperatures at most those of the printer (D7); retraction by extruder type: direct drive 0.8 mm at 35 mm/s, bowden 5 mm at 40 mm/s, unknown type (24 printers, among them every Bambu Lab printer) the direct drive values with the warning EXTRUDER_UNKNOWN; TPU: distance divided by two; a value published by the manufacturer of the filament always comes first. A value lowered by a limit gives the warning VALUE_LIMITED when it changes by at least 10 %; the limit of 100 mm/s (maxPrintSpeed null) always gives it when it lowers the value; the travel speed never gives it, neither with the limit of 150 mm/s (maxTravelSpeed null) nor with a published maxTravelSpeed (confirmed by Noam on 2026-11-06, answer A; RECOMMENDATION_RULES.md 1.1.2).
- Temperatures and cooling (D7): new field temperature {nozzle, bed} in the Recommended Profile Schema (DATA_SCHEMA.md 3.10.0). Value: the one published by the manufacturer of the filament; otherwise the middle of the range of the filament, rounded to 5 °C; without a filament, the middle of the range of the material; always at most the maximum temperature of the printer. Fan: the value published by the manufacturer of the filament; otherwise the rule of the family (RECOMMENDATION_RULES.md): PLA 90 %, PETG 50 %, ABS 15 %, ASA 15 %, TPU 40 %. Minimum layer time 5 s. These values are a choice of the recommendation, shown as such; the rule of lot 69 (no value taken in the middle of a range) applies to the data of the filaments, not to the recommendation.
- Supports and adhesion (D8): DATA_SCHEMA.md 3.10.0 follows the code: supports {enabled, type}. Supports enabled when the largest overhang angle is above 60 degrees or the longest bridge above 50 mm; type of the preset; never with the Vase preset (warning VASE_SUPPORTS_IGNORED). Adhesion: skirt by default; brim when the tip risk is at least 41 (Moderate), when the family is ABS or ASA, or when the object is tall; never a raft in Phase 10.
- Warnings (D9): the table of RECOMMENDATION_RULES.md 1.1.0 (Recommendation Warnings): 13 codes. The interface shows the translated text of the code (warning.<CODE>, three languages); the stored message keeps an English reference text, never shown; source "recommendation"; recommendedAction "". A critical warning does not block the recommendation: it is shown first, in red; nothing is blocked before the export (Phase 14).
- Confidence (D10; KI-010): 100 minus the reductions of RECOMMENDATION_RULES.md 1.1.0 (no filament -15, incomplete analysis -20, printer or filament of the user (Local Custom) -10 each, automatic classification Low -10 or Unknown -20), limited to 0 and 100; levels Excellent, High, Moderate, Low, Very Low. The confidence of the preset is no longer used.
- Start (D11): automatic, as the analysis: as soon as the analysis of an object is up to date and a printer and a material are selected. The filament is optional (filamentId null, DATA_SCHEMA.md 3.10.0). Immediate computation (rules only), without a Web Worker. New Object Reference Rule 11: a change of the printer, the material, the filament, or of the category chosen for an object makes the recommendations concerned outdated, then they are generated again at once. Without a printer or a material: no recommendation; the section shows "Select a printer and a material" (REC_002, no message over the viewport). Tools > Generate Recommendations and the toolbar button Generate generate again the recommendations of the selected objects (all the objects when none is selected).
- Interface (D12, option B): Recommendation section, one selected object: object type, preset, warnings and confidence visible; quality, infill, supports, adhesion, temperatures, cooling, speeds and retraction folded under "Details" (GUI_SPEC.md, Recommendation Section). Read-only values. Print Preset section and status bar (Active Preset): the preset of the selected object, "—" otherwise.
- Unused files (D13): the table of PHASE10-ANALYSE.md (D13) is validated; each deletion is made in the lot given and recalled in its LOTN.md: CategoryDetector, ConfidenceScorer and ClassificationEngine (src/classification_engine/) rewritten under the same names, ConfidenceScorer.isReliable removed, ClassificationValidator kept and called (KI-011); the four copies of src/optimization_engine/ removed (decision 5 of 2026-10-13 changed); DecisionEngine.shouldRecommend, calculateScore, getRecommendationLevel and WarningEngine.hasWarnings, getWarningCount removed; PresetSelector.ts removed; PresetManager.ts, PresetRepository.ts, PresetValidator.ts and src/services/PresetService.ts replaced by the loading of the presets and removed; RecommendationPanel.tsx and PresetPanel.tsx removed when the sections are done; field fanSpeed of PrintPreset removed. Any other removal is asked first.

## Consequences

Advantages:

- Every number proposed by the application is written in the documentation and validated
- The recommendation respects the printer, the material and the filament (KI-008), with a prudent value when the printer does not publish a speed
- The user can correct the type of an object, the information the application cannot guess
- The recommended profile contains the temperatures, the most important setting for the user

Disadvantages:

- Nine categories of fifteen are never detected automatically
- The thresholds of the classification are a first setting
- Many printers do not publish their travel speed: their travel is limited to the prudent value (without warning)

## Alternatives Considered

File name used as a hint of the category (D2, option B)

Rejected

Reason:

- A name is often unrelated to the content; the classification must stay geometric and explainable

Speeds as a percentage of the maximum speed of the printer (D5, option B)

Rejected

Reason:

- The published maximums are commercial values, and 15 printers publish none

Support Schema {required, type, density, overhangThreshold} kept (D8, option B)

Rejected

Reason:

- density and overhangThreshold have neither definition nor equivalent in the target slicers

A critical warning blocks the recommendation (D9, option B)

Rejected

Reason:

- The user must see the settings and the problem together; the export (Phase 14) stays the place where an object is blocked
